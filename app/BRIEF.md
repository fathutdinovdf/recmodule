# Модуль управления рекомендациями — состояние работы

Краткая справка для нового чата. Что сделано, где лежит, какие решения приняты
и почему. Подробности — в комментариях к коду, они там объясняют «почему».

## Что это

Специализированный модуль КИС «Виртуальный расходомер» по договору
ЛУКОЙЛ-Западная Сибирь (Заказчик) ↔ АКЭ (Исполнитель): экспертное сопровождение
механизированного фонда, услуги с 01.07.2026 по 30.12.2027. Исполнитель выдаёт
рекомендации по скважинам, Заказчик решает, эффект подтверждается в 90-суточном
окне.

Было: статический HTML-макет (папка `макет/`) — девять экранов, выверенный
визуальный язык, документ решений. Стало: приложение на реальных данных
(папка `app/`). **Макет остаётся эталоном вёрстки**, из него переносятся
разметка и CSS один в один.

## Стек и запуск

Next.js 15 + React 19 + TypeScript, PostgreSQL 15.5 в Docker (та же версия, что
на дев-стенде ВМАП — чтобы не написать SQL, которого там нет).

```
cd app
npm run db:up      # поднять базу (нужен запущенный Docker Desktop)
npm run dev        # актуализирует демо-данные и поднимает сервер на :3100
```

Прочее: `npm run db:seed` — пересоздать демо, `npm run db:rebase` — пересчитать
базовые значения демо по замерам ВМАП (нужен доступ на стенд), `npm run
db:refresh` — сдвинуть даты к сегодня, `npm run db:load-economy` — перезалить
ставки.

## Устройство

```
                     003_demo (якорь и сдвиг), 004_status_tone,

  src/domain/        ЧИСТЫЙ TS без Next: measurements, effect, baseline, workhours
  src/db/            pool (две базы), vmap (только чтение), economy, recommendations
  src/services/      effect-window (замеры + ставки + база), effect-store (кэш
                     расчёта), baseline (база по замерам)
  src/components/    AppShell, Icons
  src/app/           страницы; registry.css и tokens.css — КОПИИ из макета
```

**Правило, заложенное в архитектуру:** предметная логика (расчёт эффекта,
агрегация замеров, рабочие часы) живёт в `src/domain/` без единого импорта из
Next. Причина: фронт ВМАП — React 18 SPA на Vite, не Next; при встраивании
серверная половина Next не переедет, а домен переживёт смену обвязки.

`modulePool` — своя, чтение и запись. `vmapPool` — дев-стенд Заказчика,
**только чтение**, в `vmapQuery` стоит проверка, отклоняющая всё кроме SELECT.

схема `ois_vmap`. ClickHouse `vps-chdb01.ois.ru:8123` — там телеметрия, но для

## Источник данных: стенд или своя база (`DATA_SOURCE`)

На первом этапе модуль разворачивается на облачном сервере вне ландшафта
Заказчика, где стенда ВМАП нет вовсе. Поэтому всё, что бралось со стенда,
имеет вторую реализацию против своей базы, а выбор делает переменная
окружения:

| `DATA_SOURCE` | Откуда данные |
|---|---|
| не задана или `vmap` | дев-стенд ВМАП — как было, поведение по умолчанию |
| `manual` | своя база: `rec.ref_wells` и `rec.daily_facts` |

Переключение работает в обе стороны постоянно, это **не разовая миграция**:
при переносе на ландшафт Заказчика `DATA_SOURCE` убирается, и код ВМАП
возвращается в работу как есть. Выпиливать его нельзя.

**Устройство.** `src/db/wells-data.ts` — фасад, выбирающий реализацию;
все потребители (`services/baseline.ts`, `services/effect-window.ts`, мастер
регистрации, оболочка карточки) импортируют функции оттуда, а не из
`db/vmap.ts`. Сам `db/vmap.ts` при этом не менялся: у обеих реализаций одни
и те же имена и сигнатуры.

`src/db/manual.ts` отдаёт суточный факт как `Measurement[]` — тот же тип,
что и стенд, с меткой времени на начале суток. Это сознательно: домен
(`dailySeries`/`dailyAverage`) уже умеет и протяжку значения вперёд при
пропущенных сутках, и расчёт `coverage`/`points`. Введённые сутки получают
`coverage ≈ 1`, пропущенные — `0`, ровно как с замерами стенда, и в
`domain/` не меняется ни строки.

**Справочник объектов** переносится дампом, в два шага, потому что доступ к
стенду и доступ к целевой базе не бывают одновременно:

```
npm run db:dump-wells-ref   # там, где виден стенд → вмап-скважины.json
npm run db:load-wells-ref   # на целевой машине → rec.ref_wells
```

Загрузка идёт UPSERT-ом, а не TRUNCATE: скважина, по которой уже выписаны
рекомендации, не должна на секунду исчезать из справочника посреди
загрузки, а пропавшие со стенда объекты остаются — на них ссылается история.

**Суточный факт** вводится руками на экране `/manual-data` (только
Исполнитель). При работе от стенда экран доступен, но предупреждает, что
введённые числа в расчёт не идут: так их можно подготовить заранее, до
переключения. Пустое поле значит «нет данных», ноль — остановленную
скважину; путать эти два случая нельзя.

Экономика от источника не зависит: ставки НДПИ, ЭЭ, деэмульгатор и цена
нефти уже целиком локальные, `load-economy.mjs` берёт их из статических
дампов. Пласт при этом двух разных сортов: `rec.ref_wells.plast` (параметр 50
ВМАП) — информационное поле карточки, а пласт для НДПИ живёт в
`rec.econ_ndpi_rates` и приезжает из Excel-модели Заказчика.

## Расчёт эффекта — источники и формула

Формула из рабочего шаблона Заказчика «Шаблон оценки эффективности АЛЬМА»
от 05.08.2026 (лежит в корне проекта), применяется к ПРИРОСТУ к базе:

```
выручка   = Δ Qн × цена нефти
НДПИ      = Δ Qн × ставка по паре «месторождение + пласт»   ← с нефти, не с жидкости
ЭЭ жидк.  = Δ Qж(т) × ставка месторождения                 ← ЖИДКОСТЬ В ТОННАХ
ЭЭ нефть  = Δ Qн × ставка месторождения
реагенты  = Δ Qн × ставка месторождения
эффект    = выручка − НДПИ − ЭЭ жидк. − ЭЭ нефть − реагенты
```

**Жидкость в формулу входит массой.** В шаблоне столбец K — «Добыча жидкости,
т», ставка ЭЭ на жидкость (столбец N) умножается на него. ВМАП же меряет дебит
в м³/сут, поэтому прирост переводится в тонны: `liquidMass` в
`domain/measurements` — объём нефти из её массы и плотности, остальной объём
вода. Функция линейна, поэтому массу считаем прямо из приростов, и базе не
нужна собственная обводнённость. Плотности берутся у скважины: параметр 13
(нефть) и 12 (вода). Столбца Q «Дополнительные затраты» у нас нет: в шаблоне
это ручной ввод.

Прежний набор статей (подъём, ППД, транспорт, подготовка, обслуживание ГНО) — из
более ранней модели `01_2026_...xlsx`, Заказчик ей не пользуется, в модуле его
нет. Коэффициента эксплуатации нет намеренно: считаем по фактическим суткам, день
простоя приходит нулевым приростом сам, поправка задвоилась бы.

**Ставки:** 1210 скважин из 1707 фонда, 25 ставок НДПИ, 15 месторождений.
Сопоставление скважины со ставкой — по паре «месторождение + номер», НЕ по
номеру: номер уникален внутри месторождения, но не между ними, 77 скважин
получили бы ставку соседнего промысла молча.

**Базовые значения.** Договор (Приложение № 2, «Формирование базовых значений»)
описывает четыре способа. Реализован второй: средневзвешенные значения за **три**
календарных дня, непосредственно предшествующих **регистрации** рекомендации, —
`domain/baseline.ts`. Кондиционными считаются сутки с собственным замером дебита
и ненулевым дебитом; обводнённость может быть протянутой (её меряют лабораторно
и много реже — требование своего замера обводнённости оставило бы без базы
девять рекомендаций из десяти). Основной договорный способ — утверждённый
технологический режим месяца выдачи рекомендации — не реализован, но данные для
него на стенде есть: параметры 0 «Дебит жидкости Режимный» и 6 «Обводненность
объемная Режимная», 92 515 записей по 3190 скважинам.

**Демо-базы** ставит `npm run db:rebase` (`scripts/rebase-demo.mjs`) — по
настоящим замерам, тем же кодом домена. `seed-demo` пишет заглушку, потому что
работает без доступа к стенду. Запускать rebase после каждого seed и каждого
refresh: сдвиг дат демо переносит период базы на другие календарные сутки, а
замеры ВМАП настоящие и не сдвигаются.

**Замеры (факт):** параметр 1 «Дебит жидкости Замерной» + параметр 7
«Обводнённость» из `ois_vmap."WellData"`. Два места, где легко ошибиться:

1. **НЕ фильтровать по `DeleteDate IS NULL`.** DeleteDate у замера означает «на
   смену пришёл следующий», вся история — записи с проставленным DeleteDate:
   1 774 442 против 9 115 «живых».
2. **Время замера = `COALESCE(FactDate, LEAST(CreateDate, UpdateDate))`.**
   Семантика пары Create/Update в разных пачках разная; общее одно — момент
   замера всегда раньше момента записи в базу. FactDate точнее, но заполнен у
   сотни записей из девяти тысяч.

**Суточное значение** — интеграл по времени, а не среднее арифметическое
(замеры в 08:00 и 22:00 описывают куски суток разной длины). Между замерами
последнее значение протягивается: разрывы бывают до 50 суток. Известное
ограничение: остановленную скважину от скважины без замеров не отличаем —
для этого нужен параметр 16 «Состояние по ТМ».

## Демо-данные: якорь и сдвиг

Требование: на дев-версии всегда настоящие дата и время, но статусы демо не
устаревают.

Решение — в `rec.demo_state` хранится якорь (момент генерации набора).
`refresh-demo` считает разницу между якорем и сегодня, вызывает
`rec.shift_demo(days)` и переставляет якорь. Взаимное расположение событий
сохраняется полностью, меняется только привязка к календарю.

- Сдвиг, а не перегенерация — иначе терялось бы сделанное руками в интерфейсе.
- Записи без `is_demo` не двигаются: их даты настоящие.
- Сдвиг кратен суткам — иначе «утро понедельника» станет «ночью понедельника»
  и расчёт норматива в рабочих часах поедет.
- `effect_daily` при сдвиге удаляется, а не двигается: он привязан к реальным
  замерам ВМАП с их датами.

Набор: 65 рекомендаций по всем 10 статусам, 18 с окнами эффекта — все на
скважинах, по которым замеры реально есть. Есть решения, комментарии, базовые
значения, споры Заказчика (о дате реализации и о базе).

Статус «Закрыто окно» получен **досрочным закрытием**: окно в 90 суток,
открытое после 01.07.2026, к сегодняшнему дню само закрыться не успело.

## Сделано / не сделано

Готово: схема БД, экономика в базе, домен (агрегация + формула), оболочка
приложения, **реестр рекомендаций** — сверен с макетом по колонкам, ширинам,
иконкам, тегам и кружкам статусов, **сортировка, фильтры и период в шапке
реестра рабочие** (были декоративными). **Оболочка карточки** (`/rec/[id]`: шапка,
полоса ожидаемого результата, вкладки, правая колонка с параметрами скважины из
ВМАП), **вкладка «Расчёт эффекта»** со всеми блоками из решений ниже и
**вкладка «Сводка»** с первой записью из интерфейса в БД: решение Заказчика
транзакционно пишет `rec.decisions`, меняет статус и добавляет событие в
`rec.recommendation_events`. Формы учитывают роль и право принятия решения,
валидацию причины/обоснования и остаток SLA в рабочих часах. Расчёт
кэшируется в `rec.effect_daily`. Служебная страница расчёта убрана, её классы
из `app.css` удалены.

**Сортировка/фильтры/период реестра** перенесены из макета (логика была в
`app.js`: openFilterPopover/openTextPopover/openPeriodPopover, state.sort,
CTRL_ORDER) на URL-параметры и SQL вместо клиентского JS-состояния — отбор
считает сервер по всей таблице, а не браузер по одной странице, и ссылка на
отфильтрованный/отсортированный реестр рабочая сама по себе. Состав:
`db/recommendations.ts` — общий `WITH base AS (...)` CTE, где заодно посчитан
`control_kind` (бакет норматива ответа: hidden/pending/none/ok/late/overdue/
waiting) как SQL CASE, зеркальный `domain/workhours.control()` — колонка
«Контроль ответа» не лежит в БД и нигде раньше не сортировалась и не
фильтровалась, теперь можно; `columnFacet()` считает чек-лист значений со
счётчиком по всему реестру (не по текущей выборке — иначе счётчики одной
колонки менялись бы фильтром другой, как и в макете). Данные фильтра —
`GET /api/registry/facet?col=&q=` по требованию открытия поповера, а не
заранее: у «Скважины» может быть много разных значений. Клиентская половина —
`app/registry-head.tsx` (шапка `<thead>` как отдельный клиентский компонент,
колонки — общий `app/registry-columns.ts`, чтобы состав не расходился с
серверной страницей): три поповера (чек-лист, текстовый поиск, период) на
shadcn `Popover`, 3-тактная сортировка по клику на подпись колонки (включить →
сменить направление → выключить), как в макете. Анимация — animate-ui
`Highlight` (`components/animate-ui/primitives/effects/highlight.tsx`) даёт
скользящий фон у выбранного пункта периода, стрелка сортировки поворачивается
пружиной через `motion.svg` вместо CSS-transform. Для чек-листа Highlight не
взяли: его `children`-режим оборачивает строку в лишний `<div>`, ломая
flex-раскладку `.popover__row` (счётчик и подпись сходятся), а `parent`-режим
не нужен без общего выбранного значения — там осталась простая CSS
`:hover`-подсветка из `registry.css`, как в макете.

**Триггер поповера — `Hint` снаружи `PopoverTrigger asChild`, не наоборот**
(тот же порядок, что уже был в `card-actions-menu.tsx`): если `PopoverTrigger`
обёрнут вокруг `Hint`, Slot клонирует пропы (onClick и так далее) на сам
компонент `Hint`, а тот не прокидывает произвольные пропы дальше — клик молча
не открывал бы поповер.

**Не тронут `.popover` из `registry.css`** — у него `position: fixed`, а Radix
уже позиционирует `PopoverContent` сам через floating-ui; вместо класса
поповеру заданы те же отступы/ширина через Tailwind-утилиты с токенами
(`p-[var(--group-padding-s)]` и так далее), а `.popover__list/__row/__foot` и
`.field` — используются как есть, в них позиционирования нет.

Не реализовано (осталось как в макете, декоративно): перетаскивание ширины
колонок (`.resizer`) и «Настройка колонок» — выбор видимых колонок.

**Мастер регистрации открывается клиентским состоянием, не маршрутом.**
Раньше был перехватывающий маршрут `@modal/(.)rec/new` — URL менялся на
`/rec/new`, ссылку можно было скопировать. По требованию (открытое окно шарить
не нужно, черновик при перезагрузке сохранять не обязательно) заменено на
`registration-launcher.tsx`: кнопка держит `useState(open)`, справочники
(направления/приоритеты/исполнители/текущий пользователь) тянутся действием
`справочникиМастера()` из `rec/new/actions.ts` только в момент открытия —
адрес не меняется вообще. `RegistrationWizard` больше не дёргает
`router.back()`, принимает `onClose` пропом; для прямого захода по `/rec/new`
осталась обычная страница `rec/new/page.tsx` с обёрткой `standalone.tsx`
(`onClose` там — `router.push('/')`, состояния открытия у неё нет). Слот
`@modal` в `layout.tsx` и сам каталог `@modal/` убраны — перехватывающий
маршрут для этого сценария был не нужен. Черновик при закрытии/перезагрузке
не сохраняется (кроме отдельной ручной кнопки «Сохранить черновик» в самом
мастере — она была и раньше, работает через свой `localStorage`-ключ,
не автоматически); если понадобится автосохранение при F5 — обсуждали
localStorage поверх этого же launcher-а как отдельный шаг.

Начат поэлементный переход на shadcn поверх Tailwind 4 без изменения цветов
ВМАП. Уже используются Button, Calendar/Popover, Field, Dropdown Menu, Tooltip,
Combobox, Textarea, Item и Separator; Combobox сохраняет обычный контракт
HTML-формы и первым
применён к выбору причины отклонения рекомендации;
семантические цвета shadcn связаны с токенами ВМАП в `src/app/shadcn.css`,
Tailwind preflight выключен, чтобы не переопределять существующую вёрстку.
Меню действий показывает состав из `HEAD_ACTIONS`, но пункты намеренно disabled,
пока для них нет серверных операций. Tooltip покрывает кнопки-иконки в шапке,
реестре и карточке, а также сортировку, поиск, фильтры и период в таблице; у
стрелок календаря подсказок нет по решению пользователя.

**Вкладка «Реализация»** замкнула главную цепочку: регистрация → решение →
реализация → эффект. Исполнитель фиксирует дату, полноту и то, что не выполнено
при частичной; фиксация одной транзакцией пишет `rec.implementations`, переводит
статус в «Открыто окно», ставит `completeness` и включает уже готовый расчёт.
Там же разбирается спор о дате: Заказчик оспаривает дату, Исполнитель принимает
или отклоняет. Принятая дата переносит окно целиком и удаляет кэш `effect_daily`
— он посчитан по суткам старого окна. Фиксация несёт и вложения (`rec/[id]/impl/fix-form.tsx`)
— тот же `rec.attachments` с `content bytea`, что у реплик и обоснования рекомендации,
контекст `'implementation'`, лимиты те же (5 файлов, 10 МБ каждый). Список файла в форме — как
в композере обсуждения (`Attachment`-карточки), но заливка не XHR, а обычным полем формы:
скрытый `<input type=file>` синхронизируется с состоянием через `DataTransfer`, как в мастере
регистрации.

**Меню действий в шапке** (кебаб «⋯») работает целиком — `rec/[id]/lifecycle.ts`:
регистрация черновика с выдачей номера, удаление черновика, отмена, повторная
передача после уточнения, досрочное закрытие окна, новая рекомендация на основе
отклонённой. Пункт меню ведёт на вкладку с раскрытой формой, а не выполняет
действие сразу: операции необратимы, и между «нажал в меню» и «сделано» стоит
экран с последствиями. Меню видит только Исполнитель — все эти операции его.
Регистрация сама решает, уходит ли рекомендация Заказчику сразу: вне рабочего
окна она ждёт его открытия в статусе «Зарегистрировано».

**Спор о базе** замкнул вторую спорную величину — `rec/[id]/effect/actions.ts` и
`baseline-block.tsx`. Заказчик подаёт свою версию базы с обоснованием (новая
строка в `rec.baselines` со `status='proposed'`, `source='disputed'`, плюс спор
с `proposed_baseline_id`), Исполнитель принимает или отклоняет. Принятие делает
предложенную версию действующей, прежнюю — `superseded`, и удаляет кэш
`effect_daily`: каждые сутки в нём посчитаны как разность со старой базой.
Отклонение оставляет базу прежней, а предложенную версию — `rejected`, в
карточке она остаётся видимой. Формы — окном поверх карточки (ActionDialog), в
том числе подтверждение принятия: оно необратимо и стирает расчёт.

**Окна действий несут только заголовок, поля и кнопки.** Пояснения под
заголовком и строка фактов (номер, статус, остаток норматива) были и убраны по
решению пользователя: всё это стоит в самой карточке, из-под окна, и в окне
читалось повтором.

**Все формы действий теперь окном** (`ActionDialog`), а не блоком на вкладке:
решение Заказчика (принять / отклонить / уточнить), фиксация реализации, спор о
дате в обе стороны. Кнопки при этом остаются на месте — раньше форма занимала
их место, и после открытия было не видно, от чего отказываешься. Принятие даты
Заказчика получило собственное окно вместо мгновенной отправки: оно переносит
окно эффекта целиком и стирает `effect_daily`. Цена — формы требуют JavaScript;
размен тот же, что уже принят для меню действий и спора о базе.

**Три окна спора о базе открываются без навигации** — первыми из шестнадцати.
Окно стоит в разметке вкладки закрытым, открывает его состояние
(`ActionDialog` получил управляемый режим: `open`, `onOpenChange`, `trigger`),
а `?form=` задаёт лишь начальную открытость и убирается при закрытии руками.
Отказ валидации тоже перестал быть навигацией: действия возвращают ошибку
значением (`ОтветФормы` в `effect/actions.ts`), форма читает её через
`useActionState`. Раньше и открытие, и каждый отказ давали заглушку вкладки и
пересборку окна — это было видно глазом. Клиентская половина — в
`effect/baseline-forms.tsx`, серверная (что показывать и кому, справка по
замерам) осталась в `baseline-block.tsx`; справка обёрнута в `Suspense`, иначе
поход на стенд ВМАП задерживал бы вкладку ради текста внутри закрытого окна.
Цена: эти формы требуют JavaScript. Остальные тринадцать окон пока по-старому,
через адрес.

Заголовок, тон и ширина всех шестнадцати окон — в `rec/[id]/form-meta.ts`,
оттуда их берут сами окна: `<ActionDialog {...окно('reject')}>`. Файл без
`'use client'`: список читают и серверные страницы, и меню действий.

**Оставшиеся тринадцать окон переведены на тот же приём.** Открытость и
уборка `?form=` вынесены в общий хук `rec/[id]/use-dialog-state.ts`
(`useОкноДействия`), которым теперь пользуются все клиентские половины окон:
`effect/baseline-forms.tsx` (было), `summary/decision-forms.tsx` (решение
Заказчика — принять/отклонить/уточнить), `summary/lifecycle-forms.tsx`
(меню шапки — регистрация/удаление/отмена/повторная передача/копия) и
`impl/action-forms.tsx` (фиксация реализации, досрочное закрытие, спор о дате
в обе стороны). Все шесть серверных действий (`actions.ts`, `lifecycle.ts`,
`impl/actions.ts`) переписаны на тот же контракт `ОтветФормы`, что у спора о
базе: ошибка — значение из `useActionState`, а не редирект на `?err=…`.

Восемь окон с кнопкой прямо на вкладке (решение Заказчика, фиксация,
досрочное закрытие\*, спор о дате в обе стороны) получили `trigger` внутри
своего же компонента — открытие мгновенное и без навигации, один в один со
спором о базе. Пять окон из меню шапки (регистрация, удаление, отмена,
повторная передача, копия на основе) своей кнопки на вкладке не имеют:
меню — в `layout.tsx`, а окно — в дереве конкретной вкладки, разных
поддеревьях React, и без общего клиентского состояния между ними мгновенное
открытие недостижимо без более глубокой переделки (общий стор между шапкой и
вкладками). Поэтому для них `?form=…` по-прежнему единственный вход — как и
раньше, — но зато отказ валидации больше не редиректит и не мигает заглушкой:
окно уже смонтировано (гейт по статусу карточки, а не по URL) и просто читает
ответ действия. \*Досрочное закрытие окна эффекта тоже без кнопки на вкладке
— тот же случай, что меню.

Заодно ушёл `compl` из адреса вкладки «Реализация»: при отказе валидации формы
фиксации раньше полноту («полностью» / «частично») возвращали через параметр,
потому что редирект стирал состояние формы. Теперь форма не перерисовывается,
и выбор в переключателе остаётся как есть без всякой передачи через URL.

Пробовали открывать окно до ответа сервера — кнопка рисовала заглушку со
скелетоном, пока идёт навигация по `?form=`. **Откачено по решению
пользователя:** окна и так открываются быстро, а заглушка добавляла подмену
на стыке. Если возвращаться к скорости открытия, то правильный путь другой —
держать окна в разметке страницы закрытыми и открывать локальным состоянием,
оставив адрес вторым входом (перезагрузка, присланная ссылка, возврат ошибки
валидации). Тогда ждать нечего вовсе.

Скелетон остался там, где ожидание настоящее: `loading.tsx` у реестра, у всех
четырёх вкладок карточки и **у карточки целиком** — последний лежит в
`rec/loading.tsx`, а не в `rec/[id]/`: заглушка сегмента подставляется внутри
его собственного layout, а медленный тут именно `[id]/layout.tsx` (карточка,
соседи, история скважины, экономика, стенд ВМАП). Уровнем выше граница
накрывает и layout, поэтому каркас появляется сразу по нажатию на номер в
реестре. Полоса вкладок там тоже скелетон: счётчики и активная вкладка ещё
неизвестны, а настоящие подписи без подсветки читались бы как готовая полоса,
по которой почему-то нельзя нажать.

Ради этого же **оболочка переехала из страниц в корневой `layout.tsx`**: пока
`<AppShell>` стоял внутри реестра и внутри layout карточки, заглушка маршрута
подставлялась вместе с ней, и на время загрузки пропадали шапка с левой
навигацией. В корневом layout она вне всех границ Suspense — не
перемонтируется при навигации и сохраняет прокрутку. Цена: корневой layout
читает пользователя и стал динамическим (страницы и так `force-dynamic`). Каждая заглушка повторяет разметку своей страницы
(вплоть до ширин колонок реестра — таблица `table-layout: fixed` иначе прыгнет
по горизонтали), а не рисует общую сетку: смысл в том, чтобы появление данных
ничего не сдвигало.

**Вкладки карточки — сегментированный переключатель animate-ui** с едущей
подсветкой (`components/animate-ui/`, зависимость `motion`). Отход от макета,
где вкладки подчёркивались снизу. Панелей нет: содержимое вкладки — страница
маршрута, поэтому взята только полоса сегментов, каждый сегмент — `Link` через
`asChild`, `value` ведёт путь, `activationMode="manual"` (иначе стрелки
клавиатуры начали бы грузить страницы). Цвета переведены на токены: в
оригинале тема переключалась вариантом `dark:`, которого у нас нет.

## Скорость загрузки

- **Клиентский кэш маршрутов** — `staleTimes: { dynamic: 180 }`. Был ноль, и
  возврат на вкладку, где человек был секунду назад, шёл на сервер заново.
  Серверный кэш по-прежнему выключен (`force-dynamic`), а действия сбрасывают
  кэш через `revalidatePath`. Три минуты выбраны под предзагрузку вкладок: с
  прежними тридцатью секундами она успевала протухнуть раньше, чем человек
  дочитывал сводку. Плата — страница, открытая повторно в пределах трёх минут,
  показывается такой, какой её прочитали: чужое решение или смена статуса на
  ней не видны.
- **Независимые запросы идут параллельно:** карточка и пользователь, расчёт и
  скважина. Было цепочкой.
- **Вкладки предзагружаются, но после открытой, а не вместе с ней.** `prefetch`
  у ссылок выключен: он запускается по появлению ссылки в поле зрения, то есть
  одновременно с загрузкой самой открытой вкладки — пять рендеров наперегонки
  за один сервер, — и не трогает вкладки, уехавшие за край горизонтальной
  прокрутки. Вместо него `ПрогревВкладок` в `tabs.tsx`: `useEffect` (то есть
  после гидрации открытой вкладки) → пауза до простоя → остальные вкладки по
  очереди, а не залпом. Прогретое протухает вместе с кэшем роутера, поэтому
  прогрев повторяется каждые 150 секунд (`staleTimes.dynamic` = 180, обновляем
  с запасом) — иначе после минуты чтения сводки переход снова шёл бы на сервер со
  скелетоном. Активная вкладка читается из ref, чтобы переключение не
  перезапускало цикл; в скрытой вкладке браузера тик пропускается, при возврате
  прогрев идёт сразу. На деве повтора нет: там прогрев ничего не кэширует, а
  только компилирует маршрут, и второй раз это уже ничего не даёт.
  **В деве prefetch у Next отключён наглухо** — `createPrefetchURL` возвращает
  null при `NODE_ENV === 'development'`, и `router.prefetch` молча ничего не
  делает, как и `Link`. Поэтому там маршрут прогревается своим `fetch` с
  заголовком `RSC: 1`: в клиентский кэш роутера такой ответ не ляжет (это умеет
  только роутер), но маршрут скомпилируется и данные прочитаются — на деве
  задержку составляет именно это.
- **Страница эффект НЕ считает — решение пользователя, архитектурное.** Читает
  готовое из `rec.effect_daily`. Пересчёт — дело бэкенда, который в рабочем
  контуре поднят постоянно; походы на чужой стенд не должны зависеть от того,
  открыл ли кто-то вкладку. Точка входа — `POST /api/effect/recalc`
  (`recalcEffect` в `services/effect-store`), пересчитывает все открытые окна;
  на демо-наборе это 12 окон за 6 секунд. Раньше те же 90 суток тянулись со
  стенда при каждом открытии вкладки, хотя замеры приезжают раз в сутки.
  Единственное, что осталось в рендере, — холодный старт: если сохранённого
  расчёта нет ни одной строки, страница считает один раз. С появлением
  постоянного бэкенда это исключение убирается.
- **На демо роль планировщика играет подъём сервера.** `npm run dev` идёт через
  `scripts/dev.mjs`: он поднимает Next, дожидается ответа и дёргает
  `POST /api/effect/recalc`. Пересчёт фоновый, старт не задерживает.
  **Хук `instrumentation.ts` для этого не годится** — проверено и откачено:
  Next собирает его для всех слоёв, включая клиентский, а туда через `pg`
  тянется `fs`, которого там нет; модуль не собирается, и вместе с ним не
  собирается приложение — все страницы отдают 500. Заодно `pg` вынесен в
  `serverExternalPackages`, и предупреждения про `pg-native` исчезли.

Три решения, принятых по ходу, — в комментариях к `effect/actions.ts`:

- **Границы спора:** сверху — закрытие окна эффекта (по аналогии со спором о
  дате; в договоре про базу прямо не сказано), снизу — согласование
  рекомендации. До согласования отдельный спор не нужен: не согласен с базой —
  не согласовывай или запроси уточнение.
- **База по замерам показывается обеим сторонам одинаково** — и Заказчику при
  подаче, и Исполнителю при разборе, с пометкой «не позиция ни одной из
  сторон». Асимметрия превратила бы справку в подсказку одной стороне.
- **Повторный круг разрешён:** после разбора Заказчик может подать возражение
  снова, пока окно не закрыто. Мешает только незакрытый спор.

Прогнано вживую на демо-базе: обе стороны, все шесть операций меню, фиксация
(полная и частичная), спор о дате в обе стороны, спор о базе в обе стороны,
отказы валидации, попытка Заказчика разобрать собственное возражение. Снимки —
`скриншоты/реализация/`, `скриншоты/действия/`, `скриншоты/спор-о-базе/`.

**Вкладка «История и обсуждение» — чат в реальном времени.** Одна лента на
события процесса и реплики сторон: спорная ситуация разбирается по одной
хронологии, две отдельные вкладки заставляли бы сшивать их глазами. Файлы —
`app/src/app/rec/[id]/log/` (`chat.tsx` — состояние, SSE, прокрутка,
оптимистичная отправка; `composer.tsx` — ввод, упоминания, вложения;
`rows.tsx` — строки; `format.ts` — форматирование, общее для сервера и
клиента), чтение — `src/db/log.ts`, канал — `src/db/notify.ts` и
`api/rec/[id]/stream`, приём реплики — `api/rec/[id]/comment`, отдача файла —
`api/attachment/[id]`. Миграция `006_chat.sql`.

Принятые решения:

- **SSE, а не WebSocket.** Поток нужен в одну сторону, отправка идёт обычным
  POST. SSE работает штатным маршрутом Next и переезжает в SPA ВМАП как есть,
  WebSocket потребовал бы второго сервера. Оповещение между процессами — через
  PostgreSQL LISTEN/NOTIFY (триггер на `rec.comments`), а не общую память:
  писать реплику может любой процесс.
- **Соединение живёт 5 минут**, потом закрывается штатно, браузер
  переподключается сам. Вечный поток мешает dev-серверу пересобираться.
- **Вложения лежат в базе** (`bytea` в `rec.attachments`): тома у модуля нет, а
  при встраивании не будет и своего диска. Предел — 10 МБ на файл, до пяти за
  раз; `storage_key` оставлен под будущий переезд в S3.
- **Упоминания хранятся связью** (`rec.comment_mentions`), а не текстом:
  фамилия в тексте завтра поменяется, связь останется.
- **Реплика не двигает процесс.** Событие в `recommendation_events` она не
  пишет: уточнение по-прежнему запрашивается решением, а не сообщением.
- **Прогрессивной деградации нет:** без JavaScript реплику не отправить.
  Осознанный размен ради живого чата, расходится с прежним правилом «формы
  работают без JS».
- Фильтров ленты нет (были — убраны), поле ввода липнет к низу панели,
  прокрутка — общая, у панели вкладки.
- **Счётчик у вкладки живой, и его слушает не чат, а полоса вкладок.** Она
  лежит в layout карточки и переживает переходы, поэтому реплика, пришедшая
  пока человек смотрит расчёт эффекта, видна сразу: число растёт и появляется
  акцентная точка (`tab__n--new`, `tab__dot` в `card-extra.css`) — одного
  изменившегося числа мало, прежнего человек не помнит. Пока открыто само
  обсуждение, полоса канал не слушает: у чата свой, а два соединения к одному
  потоку — лишний расход и в браузере, и на сервере.
- **Вкладка обсуждения при открытии просит `router.refresh()`.** Клиентский
  кэш живёт три минуты, а догрузки пропущенного у чата нет: история приходит
  серверным рендером, дальше только канал, и свежее подключение принесёт лишь
  то, что появится после него. Свежий рендер сливается с состоянием по ключу
  (замена стёрла бы неотправленные реплики).

Список упоминаний в чате — тот же cmdk в оболочке `combo__*`, что у остальных
выпадающих полей карточки, с зеркальным въездом `comboInUp`: меню раскрывается
вверх, значит и двигаться должно снизу. Поле ввода — `Textarea`, подсказки
кнопок — `Hint`, пилюля «Новое сообщение» и «Повторить» — `Button`.

**Вкладка «Файлы»** — единая витрина `rec.attachments`: показывает все
вложения рекомендации независимо от того, приложены они к обоснованию,
решению, реализации или реплике. У файла остаются контекст, автор и дата; для
реплики виден фрагмент текста, поэтому выгрузка не отрывается от разговора, в
котором появилась. Вкладка сама файлы не загружает намеренно: материал должен
появляться в том действии или реплике, смысл которых подтверждает. Скачивание
идёт через `api/attachment/[id]`, который проверяет пользователя и всегда
отдаёт файл вложением, а не открывает потенциально опасный HTML на домене
модуля. Число файлов показано в полосе вкладок.

**Переключатель темы** — `components/ThemeToggle.tsx`, иконка в шапке. Тема
хранится в `localStorage` рабочего места (не кука и не база: серверу о ней знать
нечего), до первой отрисовки её ставит синхронный скрипт в `layout.tsx` — иначе
тёмная страница мигает светлым. `prefers-color-scheme` намеренно не слушаем.
Заодно исправлены три текстовых токена тёмной темы (решение 99, пересматривает
68): `--text-primary`, `--text-tertiary`, `--text-quaternary` переопределены в
`shadcn.css` — в выгрузке Figma они тёмные, предназначены белой подложке
`--bg-component-base`, а её в модуле нет ни в одном правиле. Правка не в
`tokens.css`: тот файл — дословная копия выгрузки.

Прокрутка страниц: системная полоса скрыта, вместо неё накладной индикатор
`components/ScrollOverlay.tsx` — появляется при прокрутке, гаснет, места не
занимает, поэтому вёрстка не сдвигается при смене длины содержимого.

Дальше по плану, в порядке ценности:

1. Мастер регистрации — там же ввод базы (готовая `services/baseline.ts`

2. Экраны «Окна эффекта» и «Подтверждённые», Акт верификации (Приложение № 5).

`node scripts/render.mjs /rec/148/impl C:\путь\снимок.png` — снимок страницы

Два места, где легко потерять час:
- **Chrome нужен свой профиль** — с профилем по умолчанию запуск при открытом

- **новый файл в проекте — снести `.next`**: dev-сервер отдаёт
  `__webpack_modules__[moduleId] is not a function` на страницу, которая
  компилировалась до появления модуля.

## Открытые вопросы — спросить Заказчика или Эльдара

1. **Период базы: 3 суток или 7.** Реализованы 3 — по договору. Семи суток в
   договоре нет ни в одном из четырёх способов, «иной расчётный период»

   фактическому режиму эксплуатации» без состояния скважины не проверить.
   Данные для этого есть — параметр 78, 3554 скважины.

   На стенде есть параметры 91 «Активная электроэнергия за предыдущие сутки,

   Δ Qж и Δ Qн, деньги считаются из них той же формулой. Отдельное поле рублей

   нужна колонка и решение, что делать при расхождении с приростами.
5. **Столбец Q «Дополнительные затраты»** в шаблоне АЛЬМА есть (ручной ввод по

6. **Первичность рекомендации** (поле макета `isPrimary`) в схеме отсутствует;

7. **До какого момента можно оспаривать базу — в договоре не сказано.** Сделано

8. **Листалка в шапке** листает реестр в порядке по умолчанию: ссылка из
   реестра не несёт фильтров и сортировки. Когда понесёт — заменить запрос
   `getNeighbours`, разметка не изменится.

## Карточка: принятые решения

**Вкладка — сегмент адреса**, `/rec/[id]/[tab]`. Шапка и правая колонка живут в
`layout.tsx` и грузятся один раз; каждая вкладка — своя страница со своими
данными. Причина: карточку пересылают друг другу, и адрес вкладки ценен сам по
себе; тяжёлый расчёт эффекта изолируется естественно и не тормозит открытие
остальных вкладок. Разметку берём из `макет/card.html` + `card.css`, css
копируем файлом, как `registry.css`.

Вкладки карточки: Сводка, Реализация, Расчёт эффекта, Аналоги, Файлы,
История и обсуждение. Вкладка «Связи» из макета убрана по решению 100:
связанные сущности будут показаны в своём контексте. **Порядок изменён против макета:**
«Расчёт эффекта» стоит третьим, сразу за «Реализацией», — реализация открывает
окно, окно даёт эффект, две вкладки об одном и том же должны лежать рядом.
Состав и порядок — в `src/app/rec/[id]/tabs-def.ts`; вкладка без своей страницы
показывается приглушённой и не кликается, как несделанные пункты левой
навигации. `/rec/[id]` без сегмента уводит на первую вкладку с `ready: true`.

### Вкладка «Расчёт эффекта»

Сверху вниз: итог в рублях с признаком «предварительный / окончательный»
(предварителен, пока окно открыто или есть незакрытый спор) → база с разбором
спора, если он есть → **прогресс окна** → график «факт против базы» → разложение
по статьям со ставками и версией модели → посуточная таблица (свёрнута, из неё
собирается Форма 5) → качество данных: сколько суток по замерам, сколько
протянуто.

**Прогресс окна — решение Эльдара, важное.** Шкала на все 90 суток: полная
шкала — прогнозный эффект (считается из ожидаемых приростов эксперта той же
формулой, см. `forecastTotal`), заполнение — накопленный факт. Прогноз **не пересчитывается** на прошедшие сутки: иначе
теряется то, с чем сравниваем. Вместо пересчёта — засечка «где факт должен быть
сейчас» = прогноз × (прошло суток / 90); по ней видно опережение или отставание.
После закрытия окна шкала показывает, попали ли в прогноз, — это материал для
оценки точности собственных прогнозов.

Если расчёт невозможен (нет ставок — таких около 30 % фонда, или нет замеров) —
объяснение, чего именно не хватает, а не пустой экран.

Расчёт кэшируется в `rec.effect_daily`: считать 90 суток заново при каждом
открытии расточительно, и он должен быть воспроизводим — в споре нужно
показать, из чего сложилась цифра, а не пересчитать по свежим данным. Правило
пересчёта: **окно открыто** — считаем заново при каждом открытии и переписываем
кэш (замеры догружаются задним числом); **окно закрыто** — отдаём кэш как есть
и на стенд не ходим вовсе. Досрочное закрытие обрезает окно по дате закрытия.

Акт верификации (Приложение № 5) на вкладку не выносим — будет отдельный экран.

## Грабли, на которые уже наступали

- **`app.css` грузится после `registry.css` и перебивает макет.** В нём не
  должно быть `.tbl`, `.panel`, `.btn`, `.field` — только собственные классы.
- **Утилиты Tailwind сталкиваются с классами макета по имени.** `block` — это
  и `display: block` у Tailwind, и блок карточки с отступом снизу в `card.css`.
  Компонент shadcn с `block` в классах молча получал 12 пикселов под каждой
  строкой. Лечится правилом `[data-slot].block { margin-bottom: 0 }` в
  `shadcn.css`; на очереди те же грабли с `card`, `panel`, `tag`, `field`.
- **`db/vmap.ts` не импортируется из служебных скриптов:** он тянет
  `next/cache`, которого у голого node нет — падает `ERR_MODULE_NOT_FOUND` на
  ровном месте. Поэтому и запросы, и коды параметров (`PARAM`) живут в
  `db/vmap-sql.ts`, у которого зависимостей нет вовсе, а `vmap.ts` их
  реэкспортирует. Новую константу, нужную скриптам, класть туда же, а не в
  `vmap.ts`.
- **Установщик shadcn перезаписывает `Button.tsx`.** Он пишет `button.tsx`, а
  Windows не различает регистр — наш кастомный Button с вариантами ВМАП
  затирается стандартным. После каждого `shadcn add` смотреть `git diff` на
  `components/ui/`.
- **Необработанный отказ в промисе убивает процесс рендера целиком.** Ошибка в
  асинхронном подписчике SSE (его зовёт EventEmitter, где ловить некому) валила
  все страницы карточки сразу с `Jest worker encountered 2 child process
  exceptions`. Настоящее исключение Next прячет — искать по `--trace-uncaught`.
- **Два процесса Next на одном `.next`** дают то же `WorkerError` и
  `Cannot find module './NNN.js'`. Перед запуском сервера убеждаться, что
  старый умер: `Get-CimInstance Win32_Process` по `node.exe`.
- **Выпадающий список в окне действия рисовался ПОД окном.** `.combo__menu`
  стоял на слое 40, окно — на 50, наружу торчал только хвост меню. Теперь 60,
  как у календаря. Слой утилит Tailwind тут ни при чём: правило вне слоёв
  перебивает их независимо от значения.
- **`table-layout: fixed` требует явной ширины таблицы** (сумма колонок), иначе
  колонки растягиваются по содержимому.
- Ноль в `OperationMode` — полноценное значение (ЭЦН), а не пустота.
- Пласт из ВМАП (параметр 50, «БС10/1») и пласт в справочнике НДПИ
  («Восточно-Придорожный») — разные системы обозначений, сопоставлять их
  напрямую нельзя. Привязка берётся из модели Заказчика по номеру скважины.
- **Любой экспорт из модуля с `'use client'` приезжает на сервер клиентской
  ссылкой, а не значением.** Константа, взятая серверной страницей из
  клиентского файла, окажется прокси-объектом и молча испортит всё, куда её
  подставят (у нас — адрес редиректа, ошибка «Invalid character in header»).
  Поэтому данные вкладок лежат в `tabs-def.ts`, а компонент — в `tabs.tsx`.
- **Пересчёт кэша идёт параллельно сам с собой:** браузер предзагружает
  страницу и тут же её открывает, два рендера делают DELETE + INSERT
  одновременно, и в READ COMMITTED оба доходят до вставки. Лечится
  `pg_advisory_xact_lock` по `rec_id` плюс `ON CONFLICT DO UPDATE`.
- Ноль в плотности нефти или воды на стенде — незаполненное поле, а не лёгкая
  нефть. Такие записи есть, и ноль обнулил бы всю нефть по скважине.
- Headless Chrome не пишет скриншот по относительному пути и в системный temp:
  нужен абсолютный путь, кириллица в нём допустима.
