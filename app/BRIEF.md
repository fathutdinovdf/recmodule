# Модуль управления рекомендациями — состояние работы

Краткая справка для нового чата. Что сделано, где лежит, какие решения приняты
и почему. Подробности — в комментариях к коду, они там объясняют «почему».

## Что это

Специализированный модуль КИС «Виртуальный расходомер» по договору
ЛУКОЙЛ-Западная Сибирь (Заказчик) ↔ АКЭ (Исполнитель): экспертное сопровождение
механизированного фонда, услуги с 01.07.2026 по 30.12.2027. Исполнитель выдаёт
рекомендации по скважинам, Заказчик решает, эффект подтверждается в 90-суточном
окне.

Было: статический HTML-макет (папка `макет/`) — девять экранов, выверенный
визуальный язык, документ решений. Стало: приложение на реальных данных
(папка `app/`). **Макет остаётся эталоном вёрстки**, из него переносятся
разметка и CSS один в один.

## Стек и запуск

Next.js 15 + React 19 + TypeScript, PostgreSQL 15.5 в Docker (та же версия, что
на дев-стенде ВМАП — чтобы не написать SQL, которого там нет).

```
cd app
npm run db:up      # поднять базу (нужен запущенный Docker Desktop)
npm run dev        # актуализирует демо-данные и поднимает сервер на :3100
```

Прочее: `npm run db:seed` — пересоздать демо, `npm run db:rebase` — пересчитать
базовые значения демо по замерам ВМАП (нужен доступ на стенд), `npm run
db:refresh` — сдвинуть даты к сегодня, `npm run db:load-economy` — перезалить
ставки.

## Расчёт эффекта — источники и формула

Формула из рабочего шаблона Заказчика «Шаблон оценки эффективности АЛЬМА»
от 05.08.2026 (лежит в корне проекта), применяется к ПРИРОСТУ к базе:

```
выручка   = Δ Qн × цена нефти
НДПИ      = Δ Qн × ставка по паре «месторождение + пласт»   ← с нефти, не с жидкости
ЭЭ жидк.  = Δ Qж(т) × ставка месторождения                 ← ЖИДКОСТЬ В ТОННАХ
ЭЭ нефть  = Δ Qн × ставка месторождения
реагенты  = Δ Qн × ставка месторождения
эффект    = выручка − НДПИ − ЭЭ жидк. − ЭЭ нефть − реагенты
```

**Жидкость в формулу входит массой.** В шаблоне столбец K — «Добыча жидкости,
т», ставка ЭЭ на жидкость (столбец N) умножается на него. ВМАП же меряет дебит
в м³/сут, поэтому прирост переводится в тонны: `liquidMass` в
`domain/measurements` — объём нефти из её массы и плотности, остальной объём
вода. Функция линейна, поэтому массу считаем прямо из приростов, и базе не
нужна собственная обводнённость. Плотности берутся у скважины: параметр 13
(нефть) и 12 (вода). Столбца Q «Дополнительные затраты» у нас нет: в шаблоне
это ручной ввод.

Прежний набор статей (подъём, ППД, транспорт, подготовка, обслуживание ГНО) — из
более ранней модели `01_2026_...xlsx`, Заказчик ей не пользуется, в модуле его
нет. Коэффициента эксплуатации нет намеренно: считаем по фактическим суткам, день
простоя приходит нулевым приростом сам, поправка задвоилась бы.

**Ставки:** 1210 скважин из 1707 фонда, 25 ставок НДПИ, 15 месторождений.
Сопоставление скважины со ставкой — по паре «месторождение + номер», НЕ по
номеру: номер уникален внутри месторождения, но не между ними, 77 скважин
получили бы ставку соседнего промысла молча.

**Базовые значения.** Договор (Приложение № 2, «Формирование базовых значений»)
описывает четыре способа. Реализован второй: средневзвешенные значения за **три**
календарных дня, непосредственно предшествующих **регистрации** рекомендации, —
`domain/baseline.ts`. Кондиционными считаются сутки с собственным замером дебита
и ненулевым дебитом; обводнённость может быть протянутой (её меряют лабораторно
и много реже — требование своего замера обводнённости оставило бы без базы
девять рекомендаций из десяти). Основной договорный способ — утверждённый
технологический режим месяца выдачи рекомендации — не реализован, но данные для
него на стенде есть: параметры 0 «Дебит жидкости Режимный» и 6 «Обводненность
объемная Режимная», 92 515 записей по 3190 скважинам.

**Демо-базы** ставит `npm run db:rebase` (`scripts/rebase-demo.mjs`) — по
настоящим замерам, тем же кодом домена. `seed-demo` пишет заглушку, потому что
работает без доступа к стенду. Запускать rebase после каждого seed и каждого
refresh: сдвиг дат демо переносит период базы на другие календарные сутки, а
замеры ВМАП настоящие и не сдвигаются.

**Замеры (факт):** параметр 1 «Дебит жидкости Замерной» + параметр 7
«Обводнённость» из `ois_vmap."WellData"`. Два места, где легко ошибиться:

1. **НЕ фильтровать по `DeleteDate IS NULL`.** DeleteDate у замера означает «на
   смену пришёл следующий», вся история — записи с проставленным DeleteDate:
   1 774 442 против 9 115 «живых».
2. **Время замера = `COALESCE(FactDate, LEAST(CreateDate, UpdateDate))`.**
   Семантика пары Create/Update в разных пачках разная; общее одно — момент
   замера всегда раньше момента записи в базу. FactDate точнее, но заполнен у
   сотни записей из девяти тысяч.

**Суточное значение** — интеграл по времени, а не среднее арифметическое
(замеры в 08:00 и 22:00 описывают куски суток разной длины). Между замерами
последнее значение протягивается: разрывы бывают до 50 суток. Известное
ограничение: остановленную скважину от скважины без замеров не отличаем —
для этого нужен параметр 16 «Состояние по ТМ».

## Демо-данные: якорь и сдвиг

Требование: на дев-версии всегда настоящие дата и время, но статусы демо не
устаревают.

Решение — в `rec.demo_state` хранится якорь (момент генерации набора).
`refresh-demo` считает разницу между якорем и сегодня, вызывает
`rec.shift_demo(days)` и переставляет якорь. Взаимное расположение событий
сохраняется полностью, меняется только привязка к календарю.

- Сдвиг, а не перегенерация — иначе терялось бы сделанное руками в интерфейсе.
- Записи без `is_demo` не двигаются: их даты настоящие.
- Сдвиг кратен суткам — иначе «утро понедельника» станет «ночью понедельника»
  и расчёт норматива в рабочих часах поедет.
- `effect_daily` при сдвиге удаляется, а не двигается: он привязан к реальным
  замерам ВМАП с их датами.

Набор: 65 рекомендаций по всем 10 статусам, 18 с окнами эффекта — все на
скважинах, по которым замеры реально есть. Есть решения, комментарии, базовые
значения, споры Заказчика (о дате реализации и о базе).

Статус «Закрыто окно» получен **досрочным закрытием**: окно в 90 суток,
открытое после 01.07.2026, к сегодняшнему дню само закрыться не успело.

## Сделано / не сделано

Готово: схема БД, экономика в базе, домен (агрегация + формула), оболочка
приложения, **реестр рекомендаций** — сверен с макетом по колонкам, ширинам,

**вкладка «Сводка»** с первой записью из интерфейса в БД: решение Заказчика
транзакционно пишет `rec.decisions`, меняет статус и добавляет событие в
`rec.recommendation_events`. Формы учитывают роль и право принятия решения,
валидацию причины/обоснования и остаток SLA в рабочих часах. Расчёт
кэшируется в `rec.effect_daily`. Служебная страница расчёта убрана, её классы
из `app.css` удалены.

Начат поэлементный переход на shadcn поверх Tailwind 4 без изменения цветов
ВМАП. Уже используются Button, Calendar/Popover, Field, Dropdown Menu, Tooltip,
Combobox, Textarea, Item и Separator; Combobox сохраняет обычный контракт
HTML-формы и первым
применён к выбору причины отклонения рекомендации;
семантические цвета shadcn связаны с токенами ВМАП в `src/app/shadcn.css`,
Tailwind preflight выключен, чтобы не переопределять существующую вёрстку.
Меню действий показывает состав из `HEAD_ACTIONS`, но пункты намеренно disabled,
пока для них нет серверных операций. Tooltip покрывает кнопки-иконки в шапке,
реестре и карточке, а также сортировку, поиск, фильтры и период в таблице; у
стрелок календаря подсказок нет по решению пользователя.

**Вкладка «Реализация»** замкнула главную цепочку: регистрация → решение →
реализация → эффект. Исполнитель фиксирует дату, полноту и то, что не выполнено
при частичной; фиксация одной транзакцией пишет `rec.implementations`, переводит
статус в «Открыто окно», ставит `completeness` и включает уже готовый расчёт.
Там же разбирается спор о дате: Заказчик оспаривает дату, Исполнитель принимает
или отклоняет. Принятая дата переносит окно целиком и удаляет кэш `effect_daily`
— он посчитан по суткам старого окна. Вложений к фиксации нет: хранилища файлов
у модуля пока нет вообще, поэтому кнопка макета «Прикрепить файл» не перенесена.

**Меню действий в шапке** (кебаб «⋯») работает целиком — `rec/[id]/lifecycle.ts`:
регистрация черновика с выдачей номера, удаление черновика, отмена, повторная
передача после уточнения, досрочное закрытие окна, новая рекомендация на основе
отклонённой. Пункт меню ведёт на вкладку с раскрытой формой, а не выполняет
действие сразу: операции необратимы, и между «нажал в меню» и «сделано» стоит
экран с последствиями. Меню видит только Исполнитель — все эти операции его.
Регистрация сама решает, уходит ли рекомендация Заказчику сразу: вне рабочего
окна она ждёт его открытия в статусе «Зарегистрировано».

Прогнано вживую на демо-базе: обе стороны, все шесть операций меню, фиксация
(полная и частичная), спор о дате в обе стороны, отказы валидации. Снимки —
`скриншоты/реализация/` и `скриншоты/действия/`.

Дальше по плану, в порядке ценности:

1. **Спор о базе** — разбор на вкладке расчёта: принять предложенную Заказчиком
   версию или отклонить. Спор о дате уже разбирается на «Реализации», делать по
   тому же образцу.
2. Остальные вкладки: Аналоги, Файлы, Связи, История и обсуждение. «История»
   ближе всего к данным: события и комментарии уже пишутся всеми операциями.
3. Мастер регистрации — там же ввод базы (готовая `services/baseline.ts`
   подставляет её по замерам), инбокс, справочники, заявки, пользователи.
4. Экраны «Окна эффекта» и «Подтверждённые», Акт верификации (Приложение № 5).

`node scripts/render.mjs /rec/148/impl C:\путь\снимок.png` — снимок страницы
headless-браузером при поднятом dev-сервере. Роль на снимке задаёт переменная

Два места, где легко потерять час:
- **Chrome нужен свой профиль** — с профилем по умолчанию запуск при открытом

- **новый файл в проекте — снести `.next`**: dev-сервер отдаёт
  `__webpack_modules__[moduleId] is not a function` на страницу, которая
  компилировалась до появления модуля.

Действия проверяются отправкой формы из консоли браузера
(`document.querySelector('.form form').requestSubmit()`) и запросом к базе
`docker exec recmodule-db psql -U recmodule -d recmodule`.

## Открытые вопросы — спросить Заказчика или Эльдара

1. **Период базы: 3 суток или 7.** Реализованы 3 — по договору. Семи суток в
   договоре нет ни в одном из четырёх способов, «иной расчётный период»
   применяется только по письменному соглашению Сторон. Меняется константой
   `BASELINE_DAYS`, но тогда в карточке нужна отметка о согласовании.
2. **Кондиционность суток** определяем беднее договора: «соответствие
   фактическому режиму эксплуатации» без состояния скважины не проверить.
   Данные для этого есть — параметр 78, 3554 скважины.
3. **База ЭЭ** вводится руками и в расчёт не входит: источника факта нет.
   На стенде есть параметры 91 «Активная электроэнергия за предыдущие сутки,
   кВт·ч», 93 «Фактическое потребление», 94 «Расчётное потребление» — договор
   при отсутствии прибора учёта предписывает четвёртый способ, через Design.
4. **Прогнозный эффект в рублях выводится, а не хранится:** эксперт вводит
   Δ Qж и Δ Qн, деньги считаются из них той же формулой. Отдельное поле рублей
   завело бы второй источник правды. Если Заказчик хочет вводить рубли —
   нужна колонка и решение, что делать при расхождении с приростами.
5. **Столбец Q «Дополнительные затраты»** в шаблоне АЛЬМА есть (ручной ввод по
   мероприятию), у нас статьи нет. Подставлять ноль молча не стали.
6. **Первичность рекомендации** (поле макета `isPrimary`) в схеме отсутствует;
   в шапке карточки на этом месте показано решение Заказчика.
7. **Листалка в шапке** листает реестр в порядке по умолчанию: ссылка из
   реестра не несёт фильтров и сортировки. Когда понесёт — заменить запрос
   `getNeighbours`, разметка не изменится.

## Карточка: принятые решения

**Вкладка — сегмент адреса**, `/rec/[id]/[tab]`. Шапка и правая колонка живут в
`layout.tsx` и грузятся один раз; каждая вкладка — своя страница со своими
данными. Причина: карточку пересылают друг другу, и адрес вкладки ценен сам по
себе; тяжёлый расчёт эффекта изолируется естественно и не тормозит открытие
остальных вкладок. Разметку берём из `макет/card.html` + `card.css`, css
копируем файлом, как `registry.css`.

Вкладки из макета: Сводка, Реализация, Аналоги, Файлы, Связи, История и
обсуждение. Седьмая новая — Расчёт эффекта. **Порядок изменён против макета:**
«Расчёт эффекта» стоит третьим, сразу за «Реализацией», — реализация открывает
окно, окно даёт эффект, две вкладки об одном и том же должны лежать рядом.
Состав и порядок — в `src/app/rec/[id]/tabs-def.ts`; вкладка без своей страницы
показывается приглушённой и не кликается, как несделанные пункты левой
навигации. `/rec/[id]` без сегмента уводит на первую вкладку с `ready: true`.

### Вкладка «Расчёт эффекта»

Сверху вниз: итог в рублях с признаком «предварительный / окончательный»
(предварителен, пока окно открыто или есть незакрытый спор) → база с разбором
спора, если он есть → **прогресс окна** → график «факт против базы» → разложение
по статьям со ставками и версией модели → посуточная таблица (свёрнута, из неё
собирается Форма 5) → качество данных: сколько суток по замерам, сколько
протянуто.

**Прогресс окна — решение Эльдара, важное.** Шкала на все 90 суток: полная
шкала — прогнозный эффект (считается из ожидаемых приростов эксперта той же
формулой, см. `forecastTotal`), заполнение — накопленный факт. Прогноз **не пересчитывается** на прошедшие сутки: иначе
теряется то, с чем сравниваем. Вместо пересчёта — засечка «где факт должен быть
сейчас» = прогноз × (прошло суток / 90); по ней видно опережение или отставание.
После закрытия окна шкала показывает, попали ли в прогноз, — это материал для
оценки точности собственных прогнозов.

Если расчёт невозможен (нет ставок — таких около 30 % фонда, или нет замеров) —
объяснение, чего именно не хватает, а не пустой экран.

Расчёт кэшируется в `rec.effect_daily`: считать 90 суток заново при каждом
открытии расточительно, и он должен быть воспроизводим — в споре нужно
показать, из чего сложилась цифра, а не пересчитать по свежим данным. Правило
пересчёта: **окно открыто** — считаем заново при каждом открытии и переписываем
кэш (замеры догружаются задним числом); **окно закрыто** — отдаём кэш как есть
и на стенд не ходим вовсе. Досрочное закрытие обрезает окно по дате закрытия.

Акт верификации (Приложение № 5) на вкладку не выносим — будет отдельный экран.

## Грабли, на которые уже наступали

- **`app.css` грузится после `registry.css` и перебивает макет.** В нём не
  должно быть `.tbl`, `.panel`, `.btn`, `.field` — только собственные классы.
- **`table-layout: fixed` требует явной ширины таблицы** (сумма колонок), иначе
  колонки растягиваются по содержимому.
- Ноль в `OperationMode` — полноценное значение (ЭЦН), а не пустота.
- Пласт из ВМАП (параметр 50, «БС10/1») и пласт в справочнике НДПИ
  («Восточно-Придорожный») — разные системы обозначений, сопоставлять их
  напрямую нельзя. Привязка берётся из модели Заказчика по номеру скважины.
- **Любой экспорт из модуля с `'use client'` приезжает на сервер клиентской
  ссылкой, а не значением.** Константа, взятая серверной страницей из
  клиентского файла, окажется прокси-объектом и молча испортит всё, куда её
  подставят (у нас — адрес редиректа, ошибка «Invalid character in header»).
  Поэтому данные вкладок лежат в `tabs-def.ts`, а компонент — в `tabs.tsx`.
- **Пересчёт кэша идёт параллельно сам с собой:** браузер предзагружает
  страницу и тут же её открывает, два рендера делают DELETE + INSERT
  одновременно, и в READ COMMITTED оба доходят до вставки. Лечится
  `pg_advisory_xact_lock` по `rec_id` плюс `ON CONFLICT DO UPDATE`.
- Ноль в плотности нефти или воды на стенде — незаполненное поле, а не лёгкая
  нефть. Такие записи есть, и ноль обнулил бы всю нефть по скважине.
- Headless Chrome не пишет скриншот по относительному пути и в системный temp:
  нужен абсолютный путь, кириллица в нём допустима.
